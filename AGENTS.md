# AGENTS.md — guidance for AI assistants

This file orients AI coding assistants working on **open-balena-extension**. Read it before making changes. (`CLAUDE.md` points here.)

## What this project is
Production extensions for self-hosted [openBalena](https://github.com/balena-io/open-balena): a **remote builder** (so `balena push` works), an **imagemaker** (web UI + scripts to build flashable device images), a **custom haproxy** ingress, integration with the community **admin dashboard**, and an opt-in **Fleet Control API** (`/fleet/v1`, see below). Core openBalena is unmodified upstream; everything here sits *around* it.

## The one mental model you must hold: internal vs public TLD
openBalena issues device endpoints under a single `DNS_TLD`. This project supports running an **internal** `DNS_TLD` (e.g. `example.local`) while reaching the instance **publicly** via a reverse proxy at `PUBLIC_TLD` (e.g. `ob.example.com`).
- The API advertises `api/cloudlink/registry2/delta.${DNS_TLD}` to devices.
- Remote devices can't resolve `*.${DNS_TLD}` → their `config.json` endpoints must be rewritten to `*.${PUBLIC_TLD}`.
- The imagemaker does this for its **`__internet`** image variant (`sed s/${DNS_TLD}/${PUBLIC_TLD}/g`); the **`__lan`** variant keeps internal names for on-LAN devices.
- **Symptom of getting it wrong:** a device shows `api_heartbeat_state: online` (API reachable) but `is_connected_to_vpn: false` forever (VPN endpoint still internal). See [docs/dns-tld-split.md](docs/dns-tld-split.md).

## Hard invariants — do not break these
1. **Builder token must match the API.** `TOKEN_AUTH_BUILDER_TOKEN` on the builder/delta MUST equal the core API's value (it's mirrored to `REGISTRY2_TOKEN`). It is generated by the API into the node process env; read it from `/proc/<node-pid>/environ`, not `docker exec printenv` (that shows only image-time env).
2. **Builder needs a plaintext Docker daemon.** The community builder CLI speaks only plaintext `tcp://host:2375`. Use the dedicated `builder-dind` (`DOCKER_TLS_CERTDIR=""`), not the TLS test dind.
3. **The bundled builder CLI expires.** `obcommunity/open-balena-builder` ships an old `balena-cli` that hard-expires (~365 days after the next major). The patched image swaps in a current standalone CLI and wraps it to export `HOME` + `NODE_TLS_REJECT_UNAUTHORIZED=0` (the builder spawns the CLI with a stripped env, so these MUST be in the wrapper, not the container env).
4. **One `balena push` at a time.** Concurrent builds race on release/service creation and fail with `"application" and "service_name" must be unique`.
5. **haproxy is the single ingress.** Validate any `haproxy.cfg` change with `haproxy -c` inside the running container (it has the certs + env) BEFORE reloading; keep a timestamped backup. The builder route needs `timeout server 3600s` (builds exceed the default 63s).
6. **Never commit secrets.** Templatize to `${ENV}`: `TOKEN_AUTH_BUILDER_TOKEN`, `IMAGEMAKER_TOKEN`, `OPEN_BALENA_JWT_SECRET`, `OPEN_BALENA_S3_*`, `PGRST_JWT_SECRET`, any `*.key`/CA/`certs/`. The `.gitignore` blocks these — keep it that way.
7. **The imagemaker is sensitive.** Its images embed fleet-provisioning credentials, so it must stay authenticated (`IMAGEMAKER_TOKEN`) and/or loopback-only. Keep its `sudo` allowlist scoped — no blanket `cp`/`docker` (each is host-root); the DB read goes through `/usr/local/bin/ob-fleets`.
8. **Public ingress must carry raw TCP, not just HTTP.** The device VPN is openVPN-over-TCP on 443. An HTTP-only front (Cloudflare Tunnel, nginx http) → device shows online but VPN never connects. Use a relay VM + WireGuard + iptables raw L4 DNAT. See [docs/public-ingress.md](docs/public-ingress.md).
9. **Registry → S3 over self-signed TLS needs trust or skip.** After a PKI regen the registry's Go S3 client won't trust the internal CA → blob push fails `x509: certificate signed by unknown authority`, release hangs in `running`. Fix: `REGISTRY_STORAGE_S3_SKIPVERIFY=true` (internal hop) or install the CA into the registry's system trust.
10. **Host-local tools need split-horizon DNS.** Tools on the host (imagemaker `config generate`) resolving `api.${PUBLIC_TLD}` hairpin out to the relay and back — flaky. Add `/etc/hosts` → local haproxy. Also: `build-image.sh` must run with `BALENARC_BALENA_URL` set (it relies on the CLI default otherwise).
11. **PostgREST needs DB roles.** A wiped/rebuilt DB loses the dcnext admin roles (`anon`, etc.); PostgREST returns `role "anon" does not exist` and its proxy `ECONNRESET`s. Recreate the roles + grants.
12. **A registry blob migration must be COMPLETE or every pull 404s.** Repointing the registry's S3 backend (e.g. minio → R2) requires copying the *entire* `data/docker/registry/v2/` tree — `repositories/` **and** every blob, including the tiny manifest/config JSON blobs. If those small blobs are missed (the big layers copy fine), the registry resolves the manifest link → can't read the manifest blob → `404 manifest unknown`, and devices stall at `Downloading 0%` with `manifest for …@sha256:… not found`. **This is a server-side store gap, NOT a device fault — do not reflash the device.** Verify blob-count parity (source vs R2) and that a real manifest serves `200` + a blob `307`s to R2 before declaring success. See [docs/registry-edge-cache.md](docs/registry-edge-cache.md).

13. **The Fleet API never returns the balena API key** — not in a response, a log line, an error/problem body, an audit row, the OpenAPI document, or argv. It reads the key from `/run/secrets/balena_api_key` (or `BALENA_API_KEY`) and only ever sends it as a bearer to pine/the builder, as the VPN proxy's Basic password, or into the CLI builder's `token` file. `BalenaError` messages carry the HTTP status and a truncated response body, never request headers. `tests/test_auth.py::test_balena_key_is_never_returned` guards this; extend it when you add a route. Env values matching `env.secret_patterns` stay masked (`***`) in responses and audit rows.
14. **`metrolla_change_control` stays free of balena specifics.** `components/fleet-api/metrolla_change_control/` is the generic half of change control and is moving into `metrolla_auth` (as `metrolla_auth.change_control`) for EdgeAPI's change control. It may import only the stdlib, `dateutil` and `cryptography` — no balena, fleets, devices, Flask or SQLAlchemy (`tests/test_change_control.py::test_module_imports_nothing_host_specific` enforces this). Fleet-specific logic (base state, items, rollouts) belongs in `fleet_api/changes.py`. Its signature check must stay byte-compatible with metrolla-cli's "Change set signatures" spec.
15. **The VPN proxy path is unproven on .183 — verify it before relying on it.** Device-level actions that go through the VPN (`reach.py` `CONNECT <uuid>.balena:80` via `vpn:3128` with Basic `root:<api key>`: EdgeAPI health in rollouts/`halt_if`, site-change fan-out) have only been tested against fakes. Before you depend on them, confirm on the real host that `GET /fleet/v1/server/health` shows `vpn` ok and `GET /fleet/v1/fleets/{fleet}/devices` shows `health.source: edgeapi`. Otherwise health silently degrades to connectivity-only. Don't claim a rollout's health gating works until that's been seen.
16. **Fleet API runs one process, opt-in and private.** gunicorn `-w 1` (the change scheduler and the build lock live in-process). The role stays off by default (`deploy_fleet_api: false`), sign-in stays off by default (anonymous `site_admin` limited to `auth.allow_networks`) and `change_control.mode` stays `open` — existing hosts must not change behaviour. Never route `fleet.<tld>` publicly while sign-in is off; the container holds the balena admin key and the docker socket.

For field-scale bandwidth, offload registry blobs to cloud object storage (R2) with blob redirect — see [docs/registry-edge-cache.md](docs/registry-edge-cache.md).

## Device access reality (important when "fixing a device")
- `balena device ssh` and the dashboard terminal both ride the **VPN**. If a device's VPN is down, neither works.
- Host SSH (`:22222`) only trusts keys baked into `config.json` `os.sshKeys` at **provision time**; this OS does **not** sync newly-registered account keys to a running device (even after reboot). So you cannot mint a key a misconfigured device will accept — fix via console or **reflash** with an image built by the current imagemaker.
- **The imagemaker bakes account keys into `os.sshKeys`** (`inject-sshkeys.sh`, run by `build-image.sh`) so `balena ssh` works on every newly-built device. Register your key (`balena key add`) **before** building. Already-flashed devices that predate this need a reflash or a console `config.json` edit.
- The `balena tunnel` / `balena ssh` path validates the VPN tunnel-server cert against the **CA bundle**, not `NODE_TLS_REJECT_UNAUTHORIZED` — set `NODE_EXTRA_CA_CERTS` to the openBalena CA bundle (root+server CA) for tunnels to work (this is also required on the dcnext `remote` service for the dashboard terminal).
- The dcnext **dashboard terminal**, unpatched, regenerates an ephemeral SSH key per session (which devices don't trust — baked `os.sshKeys` won't match) and redirects to per-session **high ports 10000–10009** (blocked by most networks / Cloudflare → blank window). Both are fixed by [docs/dashboard-terminal.md](docs/dashboard-terminal.md) / [`patch-remote-443.sh`](components/admin/patch-remote-443.sh): single **443** endpoint + SSH as `root` with a fixed device-trusted key (`/certs/device_key`) + `HOST_MODE: secure`. `balena ssh`/`balena tunnel` remains the CLI fallback.

## Deploying as an AI assistant (operational runbook)
If a human asks you to **stand this up or operate it** (not just edit files), treat it differently
from a code change: deploying mutates a real host, a real PKI, and **live devices in the field**. A
bad step can knock a fleet offline, and some state (the DB + PKI) is irreplaceable. Work the
idempotent `make` path, verify every step, and confirm before anything hard to reverse.

### The happy path (prefer this over ad-hoc commands)
1. **Preflight — `make doctor`.** Read-only, always safe. Fix tooling + DNS *first*; a missing
   wildcard `*.${PUBLIC_TLD}` is the #1 failure and devices silently won't connect.
2. **Config — `make bootstrap`** (`make ansible-config` for the Ansible vars too). Idempotent;
   it generates secrets into git-ignored files. **Never echo, log, or paste those secrets** (incl.
   the builder token read from `/proc/<node-pid>/environ`) into chat, a PR, or a commit.
3. **Deploy — `make deploy`**, or a scoped `make deploy-<tag>` (e.g. `deploy-builder`,
   `deploy-imagemaker`) to limit blast radius. Core comes up first; the builder then reads the
   API-generated token from the running core (invariant 1).
4. **Verify — don't claim success without it.** Re-run `make doctor`; then
   `curl -k https://api.${PUBLIC_TLD}/ping` → `OK`, the `builder.` route → `404` (route alive),
   and a real `balena push <fleet>`. Report the actual output; if a step failed or was skipped, say so.

### Order & dependencies (don't reorder)
- **DNS wildcard resolves** before any device is expected to connect.
- **Core before builder/delta** — they mirror `TOKEN_AUTH_BUILDER_TOKEN` from the API.
- **Validate before applying:** `ansible-playbook --syntax-check` and a `--check --diff` dry run;
  `docker compose config` for compose edits; `haproxy -c` *inside* the running container before any
  reload (invariant 5), keeping the timestamped backup.

### Safe vs. confirm-first vs. never
- **Always safe / read-only:** `make doctor`, `docker compose config`, `--syntax-check`,
  `ansible ... --check --diff`, reading container status/logs.
- **Confirm with the human first (hard to reverse):** running `make deploy`/`make up` against an
  **already-running** instance, reloading haproxy, regenerating certs/PKI, **deleting any volume**
  (`db-data`, `pki-data`, `certs-data`, `s3-data` are irreplaceable — lose them and devices can no
  longer re-auth), and anything that rewrites a live device's `config.json`.
- **Never:** print or commit secrets; fire **concurrent** `balena push` (they race — invariant 4);
  publish to an external service or expose the imagemaker unauthenticated (invariant 7).

### Idempotency & recovery
The roles are written to be re-runnable, and the `core` role uses `update: false` so a re-run
won't clobber a live deployment — but still prefer scoped tags and `--check` when iterating. Before
you rely on an instance, confirm backups of the irreplaceable state (`db-data`, `pki-data`,
`certs-data`, `s3-data` + the `.env`/overrides); the checklist is in [docs/setup.md](docs/setup.md).

### Set expectations honestly — what you *cannot* do remotely
Device SSH and the dashboard terminal both ride the VPN, and this OS won't accept a freshly-minted
key on a running device (see "Device access reality"). So don't promise to "remote in and fix" a
broken device — the real fix is console access or **reflashing an `__internet` image**. The classic
trap: a device reads `api_heartbeat_state: online` but `is_connected_to_vpn: false` — it *looks*
deployed but its endpoints are still internal. Diagnose with the TLD split, don't declare victory.

## Fleet Control API (`components/fleet-api`)
HTTP API at `/fleet/v1` on the openBalena host (haproxy `fleet.<tld>` → `fleet-api:80`): builds and finalizes releases from a git ref, wave rollouts under change control, env vars, device operations, images via the imagemaker, drift, server upkeep. Sign-in/roles/audit come from `metrolla_auth` (EdgeAPI PR #101, branch `feat/relay-auth`). Full reference: [docs/fleet-api.md](docs/fleet-api.md).

Where things live:
- `components/fleet-api/fleet_api/` — the Flask + flask-restx service. `app.py` (every route, the gate, the scheduler thread), `balena.py` (pine v6 client + supervisor proxy), `builds.py`/`builder.py`/`gitsrc.py` (clone → `/v3/build` → finalize), `changes.py` (fleet change sets), `rollout.py` (waves), `fanout.py` (site changes to device EdgeAPI), `reach.py` (VPN proxy), `service.py` (fleets, devices, env, drift), `env.py` (masking), `server.py` (health + docker upkeep), `images.py`, `settings.py` (config defaults), `models.py` (SQLite).
- `components/fleet-api/metrolla_change_control/` — generic change-control rules (invariant 14).
- `components/fleet-api/tests/` — pytest; `fakes.py` has the fake pine API, builder, VPN proxy, device EdgeAPI and imagemaker (real HTTP servers on 127.0.0.1).
- `components/fleet-api/{Dockerfile,docker-compose.yml,fleet-api.example.yaml,auth.example.yaml}` — image `metrolla-fleet-api:local`, compose project `openbalena-fleet`, config examples.
- `ansible/roles/fleet_api/` — the role (tag `fleet_api`, gated by `deploy_fleet_api`); defaults in `defaults/main.yml`, config templates in `templates/`.
- `components/haproxy/haproxy.cfg` — the `fleet.` ACLs and `backend fleet-backend`.
- `docs/fleet-api.md` — deploy, config/env, auth, every endpoint, change-control flow, VPN caveat, troubleshooting.

Tests (exact commands; metrolla-auth comes from the private EdgeAPI repo):
```bash
cd components/fleet-api
pip install -r requirements.txt -r requirements-auth.txt -r requirements-test.txt
#   or with a local EdgeAPI checkout: pip install -r requirements.txt -r requirements-test.txt <EdgeAPI>/packages/metrolla_auth
python -m pytest -q          # from the repo root: make test-fleet-api
make lint                    # repo root: shell/node lint + secret scan (what CI runs)
cd ansible && ansible-playbook --syntax-check -i inventory.example.ini site.yml
```
CI's `fleet-api tests` job needs the `EDGEAPI_READ_TOKEN` repo secret; without it the job is skipped with a warning, so a green CI run does not prove the tests ran.

When changing it:
- Keep the role templates (`ansible/roles/fleet_api/templates/`) and the `*.example.yaml` files in step with `fleet_api/settings.py`; `tests/test_units.py::test_example_configs_parse` parses the examples.
- A new write route must call `gate(<resource class>, fleet)` in `app.py` and audit masked values; reads are never gated.
- Builds stay one at a time (invariant 4 applies to the API too).

How it relates to the other Relay PRs (cross-repo contract: EdgeAPI `docs/RELAY_CONTRACTS.md`):
- **EdgeAPI** #101 `feat/relay-auth` provides `metrolla_auth` (pinned in `requirements-auth.txt`); #104 `feat/relay-core` is the EdgeAPI core that EdgeAPI's own change sets (F10/M2b) build on next; that work is where `metrolla_change_control` lands, and it provides the device `/api/v1/changes` that site-change fan-out posts to (`/api/v1/health` is what reach reads).
- **metrolla-cli** #1 `feat/mtl-cli` — `mtl fleet build/deploy/approve/status` and the GitHub Action call this API; signatures follow its README's "Change set signatures".
- **balena-fleets-metrollaprod** #18 `feat/compose-base-profiles` — the fleet repo this API builds releases from (`git.allowed_repos`), and the auth fleet env vars it may patch.
- **AutocommFrontend** #185 / **datablade** #149–#152 / **infra** #6 — the site side (pages, plugins, recordings); they don't call this API directly.

## Repo layout
- `components/` — the actual source (imagemaker, builder, haproxy, admin, fleet-api). Reference implementations; paths/domains parameterized where practical.
- `ansible/` — playbooks/roles to deploy core + extensions.
- `docs/` — architecture, the DNS split, setup, runbook, CLI onboarding, Fleet API (`fleet-api.md`).
- `CHANGELOG.md` — Keep-a-Changelog; add an `[Unreleased]` entry with every change.

## When editing
- Keep `components/` source and the `ansible/` roles in sync (a change to a script should be reflected in the role that deploys it).
- Prefer parameterizing new hardcoded hostnames/paths via the `.env` / Ansible vars (`dns_tld`, `public_tld`, `install_root`, `service_user`).
- Update the relevant `docs/` and this file when you change an invariant.
